# 学生端 V2 功能缺口审计

## 摘要

本文档对学生端 V2 改造后的功能进行全面审计，识别哪些功能已有真实接口支撑，哪些使用 fallback 或静态数据，哪些需要新增后端接口。

**审计范围：**
- 首页（HomeView.vue）
- 学习中心（CourseContentView.vue）
- 诊断页（StudentTwinView.vue）
- 作业页（StudentHomeworkView.vue）
- 行业资讯（IndustryIntelligenceView.vue）
- 设置页（ProfileView.vue）

**审计结论：**
- ✅ 已有真实数据闭环：约 70%
- ⚠️ 使用 fallback/半实现：约 25%
- ❌ 需要新增接口：约 5%

## 风险与注意事项

### 1. 数据一致性风险

**问题：** 前端计算的数据可能与后端不一致

**示例：** 待完成作业数前端计算，可能因为缓存或时间差导致不准确

**建议：**
- 优先使用后端接口返回的统计数据
- 前端计算仅作为临时方案
- 定期刷新数据，避免长时间缓存

### 2. 性能风险

**问题：** 首页调用过多 API 可能影响加载速度

**示例：** 首页需要调用知识图谱、学习进度、作业列表、提交记录等多个接口

**建议：**
- 使用 Promise.all 并行调用接口
- 考虑新增聚合接口 /api/student/dashboard，一次返回首页所需的所有数据
- 使用前端缓存减少重复请求

### 3. 用户体验风险

**问题：** fallback 数据可能误导用户

**示例：** 连续学习天数显示 0，可能让用户认为系统未记录学习活动

**建议：**
- 对于暂时无法实现的功能，考虑隐藏或显示"即将上线"提示
- 避免显示明显错误的数据（如固定的 0）
- 提供数据更新时间，让用户了解数据的时效性

### 4. 开发优先级风险

**问题：** 过度追求完美可能延误核心功能上线

**建议：**
- 优先实现 P0/P1 功能，确保核心体验
- P2/P3 功能可以在后续迭代中逐步完善
- 使用合理的 fallback 数据，确保页面可用性

   - 影响：诊断页数据准确性
   - 实现难度：低（后端增加字段）
